Motor Insurance API Gateway — Technical Reference

Developer specification for the Zimnat-controlled gateway that masks IceCash APIs, orchestrates payment-first policy issuance, handles TPILICUpdate and TPILICResult polling, generates receipts and documents, and dispatches notifications across all motor insurance quote paths.

Gateway base path/api/v2/motor
Integration partnerIceCash (ZINARA/ZBC)
Policy triggerPayment success only
Quote pathsLicence / Insurance / Combined / Comprehensive
Purpose

1. Executive Overview

The customer portal, branch screens, mobile apps, and internal systems must call Zimnat Gateway APIs only. The gateway owns IceCash authentication, request transformation, quote session storage, payment orchestration, TPILICUpdate submission, TPILICResult polling, document generation, and notifications.

Primary rule: IceCash is an implementation detail behind the gateway. Consuming channels must never call IceCash directly or store IceCash credentials. The LocationID, InsuranceCompanyID, and IceCash tokens are server-side only.

Bundle inference rule

The gateway infers the bundle from field presence. There are no explicit bundle flags.

Fields present in requestBundle inferred
No licFrequency, no radioTvFrequencyInsurance only
licFrequency present, no radioTvFrequencyInsurance + ZINARA licence
licFrequency + radioTvFrequency both presentInsurance + ZINARA licence + ZBC radio
Quote amendment rule: There is no pre-payment quote update endpoint. If a customer needs to change any detail before paying, they must generate a new quote. The /update endpoint is reserved exclusively for post-payment IceCash approval.

Private orchestration layer

IceCash token management, quote session store, payment success handling, TPILICUpdate, TPILICResult polling, document generation, notification dispatch.

Token cacheQuote session storeIdempotencyOps alert queue

  → calls /api/v2/motor/quote/*          (public)

Gateway / Orchestrator
  → calls IceCash TPILICQuote            (internal, quote stage)

9. Post-Payment Orchestration

Triggered by EcoCash SUCCESS callback or branch payment confirm. Never called directly by the portal. The gateway executes this sequence internally after payment is confirmed.

Idempotency requirement: If this flow is triggered again for the same quoteId and paymentTransactionId, the gateway must return the existing policy and must not submit a second TPILICUpdate to IceCash.

Errors and Retries

12. Errors and Retries

ErrorCodeGateway actionPortal action
Token expiredEXPIRED_TOKEN Auto-refresh token and replay original request (not yet implemented — known defect) Show generic error. Retry after re-auth.
IceCash unavailable at quoteICECASH_TIMEOUT Return partial quote with status: UNAVAILABLE for affected vehicles Surface unavailable notice. Allow retry.
IceCash approval failedICECASH_APPROVAL_FAILED Raise ops alert. Do not generate documents. Log for manual reconciliation. Show payment received but policy activation in progress. Do not show failure to customer until ops resolves.
TPILICResult timeoutICECASH_RESULT_TIMEOUT Raise ops alert. Schedule retry (max 3, 30s apart). policyStatus: PENDING. Poll again.
EcoCash callback not received— Portal polling exhausts 10 attempts. Gateway checks ledger independently. Show timeout. Advise customer not to retry payment. Contact support.
Duplicate payment trigger— Idempotency guard: detect same quoteId + paymentTransactionId. Return existing policy. No action needed — transparent to portal.
Security

13. Security

Public API layer

  • JWT validation on every public endpoint
  • JWT carries masterId — must match customerReference in quote requests
  • Rate limiting on quote and payment endpoints
  • All values sent as strings to IceCash — gateway handles type coercion

IceCash integration layer

  • IceCash credentials — server-side only, never in API responses
  • LocationID — environment variable, never hardcoded, never logged
  • InsuranceCompanyID (24) — server-side constant
  • EcoCash callback endpoint — IP allowlisted to EcoCash CIDR ranges
  • Idempotency key on all orchestration triggers
OI-001 LocationID: This is a ZINARA-assigned, environment-specific value. It must be stored as an environment variable (dev/staging/production each have a different value). It must never appear in logs, responses, or frontend payloads. Obtain from IceCash partner account owner before live testing TPILICUpdate.
Known Limitations and Open Items

14. Known Limitations and Open Items

OI-001
LocationID pending. ZINARA-assigned, environment-specific. Required on every TPILICUpdate. Blocks live testing of post-payment orchestration. Obtain from IceCash partner account owner.
KD-001
stampDuty and governmentLevy swapped in coverage-options. Current response: stampDutyRate:0.03, governmentLevyRate:0.05. Correct: stampDutyRate:0.05 (5%), governmentLevyRate:0.12 (12%). BLOCKING — portal will display incorrect premium breakdown until fixed.
KD-002
insuranceType returned as single object, not array. coverage-options returns a single insuranceType object. Should be an array of 3 offered types (RTA, FTP, COMP) each with pricingType field.
KD-003
vehicleTypes uses multiplier model. Multipliers are not the correct rating approach. Should be per-vehicle-type, per-cover-type actual rates for STANDARD scheme codes (1,6,7,19). All other 33 codes should carry rates:null.
KD-004
customerReference echoes externalReference. On combined and comprehensive paths, the response customerReference field returns the externalReference value instead of the submitted masterId. Backend must pass masterId through to IceCash for cross-system linkage.
KD-005
Token auto-refresh not implemented. EXPIRED_TOKEN causes request failure. Gateway must automatically refresh the token and replay the original request without surfacing the error to consuming channels.
KD-006
suburbId casing inconsistent. owner returns suburbId (lowercase d), policyHolder returns suburbID (uppercase D). Correct field name is suburbID throughout.
KD-007
InsuranceType code 3 mapping unconfirmed. Real API response for insurance-only returns InsuranceType:"3" for a vehicle with declared value $25,000, suggesting code 3 may be Comprehensive in practice. Appendix a.2 lists code 3 as FTPF. Needs confirmation with IceCash before mapping is finalised.
KD-008
InnBucks and OneMoney IceCash payment method codes unknown. IceCash paymentMethods list includes EcoCash (3), Netone (5), Telecel (6) but no InnBucks or OneMoney codes. TPILICUpdate PaymentMethod field requires a valid IceCash code. Confirm with IceCash what code to submit when customer pays via InnBucks or OneMoney.
KD-009
vehicleType use field incorrect in enums. Codes 2, 3, and 4 return use:"Private Use" instead of "Business use", "Fleet", "Private Hire". Portal must use its own mapping table. Backend seed data fix required.
KD-010
Comprehensive response missing IceCash section. Current response does not include the merged IceCash vehicle and licence data. The recommended response shape (Section 7.4) defines the target structure including icecash{} and totals{} sections. Backend implementation required.
